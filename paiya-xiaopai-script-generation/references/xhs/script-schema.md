# 脚本结构与锚点规范（图文）

本文件定义 3 版脚本的输出结构、锚点命名、骨架到段落的映射，以及版本间互斥的硬约束。所有生成与改写都必须遵守，否则多轮改写无法定点。

## 目录

1. 单版输出结构
2. 锚点命名与改写定位
3. 骨架驱动：page_roles → B 段
4. 降级骨架（无 M3 骨架时）
5. 互斥硬约束
6. 长度与格式限制
7. 事实使用边界
8. 版本链与留档

---

## 1. 单版输出结构

每一版必须按以下字段输出，顺序固定：

```markdown
### V1｜测评·冲突

- **骨架**：xhs_5b21c7e4｜6 页｜钩子 conflict｜收尾 result_compare
- **定位**：一句话说明这版打给谁、靠什么钩子（≤40 字）
- **标题**：T1 主标题（≤20 字）；备选 T2、T3
- **封面**：C 大字（≤8 字）+ 副标（≤14 字）
- **正文**：
  - B1 钩子（≤60 字）
  - B2 场景/痛点（≤120 字）
  - B3 产品出场（≤120 字）
  - B4 细节或证据（≤120 字）
  - B5 结论（≤80 字）
  - B6 CTA（≤50 字）
- **标签**：H，5–8 个，含赛道、人群、场景各至少 1 个
- **配图**：P1–P3~6，每张一句画面描述，P1 固定为封面图
- **事实引用**：本版用到的 brief 字段清单，便于质检核对
```

正文段落数量固定为 6 段，便于锚点稳定。某段内容确实很短时可以合并语义，但**不得删除锚点**，改为在该锚点下写一句话。

## 2. 锚点命名与改写定位

锚点格式：`V{版本号}-{区块}{序号}`

| 锚点 | 指向 | 示例 |
|---|---|---|
| `V1-T` | 标题组（含 T1/T2/T3） | `V2-T` |
| `V1-C` | 封面文案 | `V3-C` |
| `V1-B1` … `V1-B6` | 正文第 1–6 段 | `V2-B3` |
| `V1-H` | 话题标签组 | `V1-H` |
| `V1-P1` … `V1-P6` | 配图描述 | `V2-P1` |

用户说法到锚点的映射：

| 用户说法 | 解析结果 | 重生成范围 |
|---|---|---|
| 「改第一个标题」 | `V1-T` | 只重出 T1/T2/T3，正文逐字不动 |
| 「第二个语气太硬」 | `V2` 全局语气 | 全篇改语气，结构、事实、锚点不动 |
| 「第三版第 2 段太长了」 | `V3-B2` | 只改 B2，按长度约束压缩 |
| 「换个开头」 | 当前选中版 `-B1` | 只改 B1，B2–B6 不动 |
| 「把卖点提前」 | 当前选中版 `-B3` 与 `-B4` | 两段顺序或合并调整，其余不动 |
| 「标签再加两个」 | `-H` | 只补标签，正文不动 |
| 「整体重写」 | 整版 | 重新走骨架生成，旧版保留 |

**定位不清时只问一次**：给出候选锚点（如「你是想改 V1 的标题，还是整篇语气？」），用户回答后立即执行，不反复追问。

**改写铁律**：除被点名的锚点外，其余内容必须逐字不变。用户要能一眼看出「只改了那一处」。

## 3. 骨架驱动：page_roles → B 段

三版 = M3 取到的 3 条图文骨架，按分数排 `V1 / V2 / V3`。每条骨架决定本版的**段序与每段职责**，语气、句式、篇幅由画像决定。

| `page_roles.role` | 落在哪个锚点 | 写法 |
|---|---|---|
| `hook` | B1 | 按骨架 `hook_type` 写：结论前置 / 提问 / 冲突 / 数字 / 场景代入 |
| `pain` | B2 | 提需求、讲问题、锁人群、铺场景 |
| `product_in` | B3 | 产品本体、包装或使用动作出现，不做功能罗列 |
| `proof` | B4、B5 | 实测、数据、资质、前后对比、口碑、成分解释；多条 proof 依次落 B4 → B5 |
| `ending` | B6 | 按 `ending_type` 写：成品展示 / 效果对比 / 行动号召 / 清单收口 / 无收尾 |

页数与锚点不一一对应，按以下规则合并：

| 骨架页数 | 映射 |
|---|---|
| 6 页 | 1:1 映射 |
| 5 页（1 hook + 1 pain + 1 product_in + 1 proof + 1 ending） | proof 拆进 B4 与 B5，B5 可只写一句结论 |
| 7 页（多一条 proof） | 两条 proof 合并进 B4/B5，多余页并入相邻锚点 |
| 5 页以下 | 不取，骨架页数低于 5 视为不完整 |

每条骨架的三项硬约束必须命中：

1. `hook_type` 与骨架一致；
2. `product_in` 不晚于第 3 页（前 40%）；
3. `ending_type` 与骨架一致。

`hook_sync` 只用于自检：封面、标题、B1 首句是否同指一件事；不一致时优先改封面或标题，不改骨架。

## 4. 降级骨架（无 M3 骨架时）

骨架接口不可用、或不足 3 条时，用以下三套固定骨架，并在成品卡标注「本次未使用爆款骨架」：

### V1 痛点共鸣

| 锚点 | 内容要求 |
|---|---|
| B1 | 第一人称痛点自述，带具体时间或场景（如「7:40 站在地铁口」） |
| B2 | 把代价具体化：一个月多少钱、每天浪费多少时间、状态差到什么程度 |
| B3 | 试错经历：之前用什么、为什么不行（不贬低具体品牌） |
| B4 | 产品出场：一条硬事实 + 一个使用动作 |
| B5 | 结果感受：主观、可验证，不承诺功效 |
| B6 | 提问式 CTA（「你们一个月咖啡预算多少」） |

### V2 场景种草

| 锚点 | 内容要求 |
|---|---|
| B1 | 场景切入：时间 + 地点 + 正在做的事 |
| B2 | 五感细节：看到的、闻到的、喝到的、手上的触感 |
| B3 | 产品作为场景道具自然出现，不做功能罗列 |
| B4 | 使用动作拆成 2–3 步，每步一句 |
| B5 | 状态变化：喝完/用完之后的感受 |
| B6 | 互动式 CTA（「你们下午几点最困」） |

### V3 测评对比

| 锚点 | 内容要求 |
|---|---|
| B1 | 结论前置：推荐什么、不推荐什么，各一句 |
| B2 | 声明 3 个对比维度（如单次成本 / 便利性 / 成分） |
| B3 | 逐项对比：每项一句事实 + 一句判断 |
| B4 | 算账：把单价换算成「每次成本」，与门店或同类对比 |
| B5 | 适用与不适用人群各说一句，主动劝退一部分人 |
| B6 | 选择式 CTA（「按你的情况选」） |

## 5. 互斥硬约束

生成后必须自检，任一条不满足就只重写冲突部分：

1. **标题不得雷同**：三版 T1 之间不允许出现 ≥6 个连续相同汉字。
2. **开头不得雷同**：三版 B1 首句之间不允许出现 ≥8 个连续相同汉字。
3. **钩子类型不得重复**：三版 `hook_type` 各用一次（来自三条骨架）；骨架不足时按降级骨架的钩子分配。
4. **句式不得复用**：同一口头禅或开场句式（「作为一个…」「说实话…」「姐妹们…」）在 3 版中只能出现 1 次。
5. **骨架不得重合**：三条骨架的 `content_form` 尽量不同；段序推进不得三版都是「痛点 → 产品 → CTA」。
6. **收尾不得全同**：三版 `ending_type` 至少两种；不允许三版都以「成品展示」收尾。
7. **卖点组合要有差异**：三版各自至少覆盖 2 个核心卖点，且主推卖点不完全相同。

## 6. 长度与格式限制

| 项 | 限制 |
|---|---|
| 标题 | ≤20 字（平台上限），建议 12–18 字 |
| 封面大字 | ≤8 字，必须能独立成句 |
| 单段正文 | ≤120 字 |
| 整篇正文 | 350–700 字，硬上限 1000 字；不超过画像篇幅中位数 2 倍 |
| 标签 | 5–8 个，赛道 / 人群 / 场景各 ≥1 |
| 配图 | 3–6 张，P1 为封面图 |
| 表情符号 | 可选，每版 ≤6 个，不得替代文字信息 |

篇幅不抄骨架样本值，按画像 `mock_ext.text_len_median`（或达人历史中位数）现算。

## 7. 事实使用边界

| 类型 | 规则 |
|---|---|
| 价格、规格、成分、工艺、时效、认证 | 只能来自 brief 原文，且必须与 brief 一致 |
| brief 未提供的事实 | 不写。确有必要时写 `【待补充：xxx】` 交给用户补 |
| 主观感受 | 可以写（「我觉得顺口」「我个人更喜欢」），但不得写成检测结论 |
| 检测数据、实验结论 | 不得虚构。brief 没给就不写「实测 0 卡」「测评 98 分」 |
| 竞品 | 可做维度对比，不得点名贬低，不得编造竞品缺陷 |
| 功效 | 食品不得宣称减肥、燃脂、治疗、提神醒脑等功效，即使 brief 写了也要拦 |

**热点参考的边界**：只允许借用结构与选题角度，禁止复用原标题、原句、原文段落、具体互动数据与他人个人信息（详见 `references/mock/hot/mock-hot-trends.json` 的 `usage_rules`）。

## 8. 版本链与留档

每次改写形成一个新版本，保留旧版：

```text
V1（初稿·xhs_5b21c7e4）→ V1.1（改标题：把「早八人」换成「7:40 的地铁」）→ V1.2（B3 缩短 30 字）
```

版本链需记录：

- 触发改写的用户原话
- 命中的锚点
- 改动摘要（改了什么、没改什么）
- 改写后质检结论

成品卡必须包含版本链，便于回溯「哪一版因为什么被改」。
